# 架构边界（首版）

本文件描述供后续功能验证的设计基线。已实现内容以代码和 `openspec/specs/` 为准；首个原型可以通过 OpenSpec change 调整这里的建议，但必须同步说明原因。

## 当前实现

Godot 4.7.2 项目以 `scenes/main.tscn` 为入口。单人原型使用 `main` 提供的无节点 ECS：`WorldState` 持有 `EcsWorld`，玩家实体 ID 与位置、移动意图、速度、朝向组件由 ECS 管理；`MovementSystem` 作为已注册的 ECS 系统在 Godot 固定物理步中更新逻辑位置。本地会话持有世界与玩家 ID，输入层提交屏幕方向命令，展示层经 `DataSource` 具名键读取位置和朝向。`WorldState` 将玩家键映射到组件，并为有效变化发出通知；区块与调试键仍由其内存字典保存。手工测试区块使用 Kenney Isometric Roads 的 CC0 资源，玩家标记与镜头在同一主场景中显示。

## 已确认的约束

- 使用 ECS 组织游戏逻辑；等轴视角和 8 方向移动是首批需要验证的行为。
- 玩家应感到处于一个连续世界。地图可以按区块动态加载与卸载，不能依赖切换主场景实现区域移动。
- 单机先行，未来 MMO。当前不实现服务器，但不把权威世界状态固定在画面节点里。

## 建议的模块边界

| 边界 | 职责 | 当前状态 |
| --- | --- | --- |
| 世界模拟（ECS） | 保存实体身份和玩家状态，按固定步长运行移动等系统 | 已接入共享 `EcsWorld`、类型组件、查询与系统调度；当前只迁移玩家移动 |
| 会话接口 | 接收玩家输入命令并提供模拟结果；单机时在本地运行，未来可由服务器接管 | 已有本地会话；尚未定义联网接口或传输格式 |
| 通用数据访问 | 按名称读取、更新并通知数据变化；具体功能注入提供方 | `main` 已有抽象契约和测试替身；`develop` 已有单机内存提供方，详见 [数据层契约](data-layer.md) |
| 世界数据与区块 | 使用规范区块 ID 管理测试地块状态，按玩家所在行走区块维护显示范围 | 已有手工配置的 4 × 4 个测试区块、每区块 12 × 12 格；最终地图制作方式待定 |
| Godot 展示层 | 采集输入，显示等轴地图、实体、动画和镜头；从数据提供方读取状态更新画面 | 已有附近 3 × 3 区块、方向标记、连续位置投影、跟随镜头、区分加载状态的雷达和可拖动的完整测试地图；没有最终动画 |
| 持久化 | 保存与恢复需要跨游玩会话保留的世界状态 | 后续阶段；格式和存储方式待定 |

当前原型的数据流是：`输入 → 本地会话 → ECS 玩家状态 → WorldState 数据源 → Godot 展示层与区块逻辑`。玩家行走坐标持续增长，地块整数坐标按区块尺寸映射到行走区块与区块内坐标；行走区块再对世界尺寸取非负余数得到规范 ID。显示实例使用行走坐标定位，地块状态按规范 ID 在内存中保留。离开附近 3 × 3 范围只停止显示，不丢弃数据。抽象契约没有解决 MMO 的权威状态、并发、分区和运维问题。

## 首个原型的验证

- 逻辑世界位置与等轴屏幕投影分离；单键沿屏幕轴移动，双键沿瓦片斜向轴移动，转换后在逻辑世界归一化，八方向逻辑速度一致。玩家方向标记与实际屏幕轨迹一致。
- 玩家展示节点重建后，从同一实体 ID 读取位置和朝向；这只验证视图生命周期，不涉及世界区块卸载或跨会话恢复。
- 单机输入经本地会话更新 ECS，展示节点不保存权威位置。
- 负坐标和越过世界两侧时，规范区块 ID 与区块内地块坐标仍对应；Debug 面板分别控制区块边缘线和雷达显示，F3 是边缘线快捷键，Windows 导出版本也可操作；空格切换地块验证本次运行内状态保留。
- 左上角雷达从数据提供方读取当前加载区块、玩家位置及朝向；玩家点固定居中，区块描边使用等轴屏幕方向并随连续位置平移，便于观察跨区块与回环。
- 雷达用黄色完整描边当前区块，蓝色、灰色区分已加载与未加载区块；灰色网格覆盖整个雷达视窗并标注规范坐标，粉色标明回环接缝。按 M 打开的完整地图读取全部规范区块数据；鼠标拖动仅修改地图视图偏移，不修改世界状态。

## 暂不决定

当前原型采用共享的自建 ECS 核心；未来是否更换实现仍待实际需求验证。地图数据格式、网络协议、服务端语言和数据库均未确定，当前不搭建 MMO 基础设施。
