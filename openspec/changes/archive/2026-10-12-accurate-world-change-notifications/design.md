# Design

## Context

`WorldManager.send_event()` 目前读取 `WorldCommandEvent` 的两个可写布尔标记；处理 System 各自负责设置。`step()` 已通过玩家状态和加载列表前后比较通知，但不覆盖事件期间的区块子实体变化。

## Goals / Non-Goals

**Goals:** 让世界边界统一判断其公开视图对应的实际变化，避免事件对象和 System 的通知标记成为真相来源。

**Non-Goals:** 不改变事件路由的布尔结果、不收拢会话入口、不拆分管理器职责。

## Decisions

- 在处理事件前后获取轻量的可观察世界快照，比较玩家位置与朝向、区块配置与加载列表、地块数组、区块子实体可见状态以及调试开关；按类别最多发一次信号。相比让事件报告结果，这能同时防止伪造和漏标。
- 区块子实体比较基于当前活跃区块的实体树与持久化组件数据；当前怪物的可见位置由其位置组件决定。移动意图虽然在事件阶段更新，玩家通知仍在 `step()` 发生。
- 移除事件变化标记及 System 对它们的赋值，避免留下误导性 API。直接用于初始化和测试布置的写入入口继续按其自身的实际变化发信号。

## Risks / Trade-offs

- 每次事件都复制活跃地块并读取区块实体，增加原型运行时开销 → 地块规模小且交互以单次事件为主；测试检查现有移动场景。若后续规模扩大，再用内部版本计数优化，保持同一通知契约。
- 快照仅覆盖公开玩家、区块和调试视图所需状态 → 新增视图类型时须把对应状态纳入快照及测试。
