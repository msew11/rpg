# Design

## Context

见 proposal.md。不同账号 LoginActor 并行处理请求，角色三表按全局 RoleId 命名，摘要周期落地。Handler 不执行文件 IO，旧 Server 仅由回归测试显式装配。

## Goals / Non-Goals

目标是在同一服务器数据目录内保证所有新角色编号唯一，正常或异常重启、删除和摘要尚未保存均不复用已经返回的编号。不同独立服务器目录不提供跨服唯一性；不迁移旧数据，不修改旧 Server 回归链路。

## Decisions

1. 使用持久化递增序列，起点沿用 1003，不含账号、时间或随机位。比随机截断整数能严格避免碰撞，比雪花算法少时钟回拨和节点号配置前提。
2. `RoleIdGenerator` 用异步互斥锁分配，`RepoRoleIdSequence` 每次预留最多 256 个编号。`role_id_sequence.json` 保存已预留的最大值；先写临时文件并刷盘原子替换，再发放编号。重启丢弃未使用部分，不要求连续。预留期间使用同目录独占锁文件，其他实例竞争失败可重试，不回退到内存编号。
3. 账号摘要仓库提供统一取号入口，复用同一个生成器；LoginActor 在同一回合先用摘要缓存校验创建意图，再异步取号，将当次编号交给 Context，Handler 仅提交内存摘要。finally 清除当次编号，避免后续消息复用。缓存提交再次校验，保持独立调用的业务契约。
4. 缺失编号文件视为全新目录；不扫描旧账号或角色文件。损坏、低于初始基线、写入失败及 int64 耗尽均拒绝，不静默重置。部署先清除旧角色数据。持久性沿用现有 StorageJson 的单文件原子替换和操作系统边界。

## Risks / Trade-offs

- 重启或多实例预留导致跳号：编号只表示身份，不承诺连续或按响应时间排序。
- 删除或回滚编号文件会破坏唯一性：文件属于服务器持久化状态，不能单独重置；本次按用户授权清除整套旧角色数据。
- 同数据目录的独占锁竞争会使当次请求失败：保留现有错误链路，重试可继续；不支持多个服务器共享业务存档运行。

## Migration Plan

确认本机游戏进程已关闭，清除 user://server 下旧、新角色摘要、三表及相关 pending 文件和 user://settings/roles 中角色设置；保留系统设置与地图。运行检查后在 develop 本地提交，完成 specs 同步与 change 归档。
