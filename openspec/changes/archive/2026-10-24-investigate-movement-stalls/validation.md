# 移动性能诊断与优化

## 环境与复现方式

2026-10-24，Windows，Godot 4.7.2 .NET，D3D12 Forward+，AMD Radeon RX 7900 XTX。使用项目原有 1280×720 设置，禁用 VSync、限制 120 FPS；Rider MCP 返回无调试会话，系统仅有编辑器进程，没有可分析的原告警快照。

```powershell
& 'D:/Program Dev/Godot_v4.7.2-stable_mono_win64/Godot_v4.7.2-stable_mono_win64_console.exe' --path D:/proj/todog/rpg --disable-vsync --max-fps 120 res://tests/movement_performance.tscn
```

诊断使用独立临时设置及服务端目录，退出清理，不读取或覆盖用户角色存档。复用正式控制器与服务流程，直接经 World.HandleInput 的输入契约每 90 个渲染帧改目标，保留真实网络确认、刷盘、ECS、角色动画、相机与地图更新。静止后采样连续移动 720 帧，结束输入后的 120 帧可能仍在移动，不代表角色已停下。

## 发现与结果

原实现每个 8×8 分块逐格调用 DrawColoredPolygon 和 DrawPolyline，共 128 条画布绘制命令。优化为一次构建并缓存二维 ArrayMesh 和网格线，每块用 DrawMesh 与 DrawMultiline 两条命令提交，离树时释放网格。

| 测量 | 原实现第 1 次 | 原实现第 2 次 | 优化第 1 次 | 优化第 2 次 |
| --- | ---: | ---: | ---: | ---: |
| 世界初始化完成 ms | 338.43 | 329.65 | 327.27 | 330.11 |
| 进入后 60 帧最长帧 ms | 221.92 | 215.19 | 47.71 | 29.53 |
| 移动 p95 ms | 8.38 | 8.38 | 8.38 | 8.37 |
| 移动 p99 ms | 15.11 | 14.81 | 13.57 | 13.48 |
| 移动最长帧 ms | 24.35 | 42.47 | 23.54 | 34.69 |
| 移动超过 50 ms 帧数 | 0 | 0 | 0 | 0 |
| 移动阶段 Gen0 回收次数 | 0 | 0 | 0 | 0 |

原实现第二次测量在优化测量之后运行，仍出现 215 ms 首帧，降低了单纯缓存预热导致差异的可能性。当前证据支持地图首次绘制是可优化的实际热点；持续移动已有较稳定帧时间，不能宣称消除了原图的秒级告警。

批量几何使用更大的数组，首次显示阶段全进程托管分配约由 19.8 KB/帧升至 29.9 KB/帧，稳态静止约 430 B/帧；这是降低托管/原生调用次数的有限内存开销，全部测量阶段未触发 Gen0。性能场景自身的采样列表也计入分配，数值不代表纯业务分配。

## 仍未确定的告警原因

没有复现 5.8–11 秒停顿，无法确认截图的 UI freeze 是游戏实际停顿、调试器暂停、窗口事件循环判定还是原生渲染等待。CPU 9% 和约 13 MB 托管内存不能单独证明性能问题或内存泄漏。godotsharp_method_bind_ptrcall 是 C# 调用 Godot 原生 API 的通用入口，单看名称无法定位具体调用。

若仍出现秒级告警，应在原运行方式下捕获包含告警区间的 dotTrace Timeline 快照，再按时间区间分析主线程运行/等待及原生调用栈。当前 Rider MCP 能分析已保存的快照，但未提供直接开始 dotTrace 采集的工具；本次使用实际图形帧测量完成定位，没有伪造性能快照结论。
