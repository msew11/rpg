# Design

## Context

当前世界组件持有全部规范区块地块；`loaded` 只是显示范围。`LocalSession` 保存时遍历所有地块，`WorldMap` 也读取全部地块。ECS 核心没有父子关系。见 proposal.md。

## Goals / Non-Goals

**Goals:** 活跃地块与会话工作存档边界清楚；正式槽位仅由会话调用者选择和提交；错误可见且不阻碍内存卸载。

**Non-Goals:** 引入怪物玩法、跨运行恢复当前尚不存在的怪物组件、网络同步或数据库。

## Decisions

1. **通用父子实体先在 `main` 实现。** 核心 `IEcsWorldData` 保存父索引，`EcsWorld` 提供指定父实体创建、查询子实体、级联销毁。核心不依赖存档文件；世界层实现“收集并落地后销毁”的卸载操作。玩家创建在世界实体下，区块创建在世界实体下。相较把文件操作放进核心，这保持 `scripts/core/` 的通用性和分支归属。
2. **地块仍在 `WorldChunksComponent`，但只保存活跃规范区块。** 配置提供 `chunk_size` 与活跃窗口尺寸。玩家坐标决定首次和后续活跃行走区块；规范 ID 用于查找同一份地块状态。活跃窗口可能在回环后多次引用一个规范 ID，因此只有最后一个行走实例退出时才释放该规范数组。世界层管理区块实体与活跃引用。
3. **初始配置为不可变基准，临时存档保存差量。** 每个发生变化的规范区块存一份紧凑完整 tile 字节数组，未变化的区块无记录。文件索引按规范 ID 唯一。加载活跃区块时先从配置生成，再覆盖临时存档记录。相比逐格 JSON 差量，这避免大范围改动时记录膨胀，也便于替换和删除记录。
4. **临时存档是每会话唯一工作文件。** 启动时清理残留工作文件；新游戏创建空工作文件；读档时将经验证的正式文件复制为工作文件。`DataCache`/会话存储服务只读写工作文件。点击保存时，调用者让活跃数据覆盖工作文件的对应记录，再将完整工作文件提交所选正式槽位。先写新文件再替换目标文件；正式写失败不改变原槽位。
5. **组件格式由组件提供，记录外层保存稳定类型和实体标识。** 需要落地的组件实现 `ToPersistedString` / `FromPersistedString`；不需落地者返回空标记。实体落地记录含稳定键、父键、组件类型键与版本，避免依赖运行时递增 ID。当前地块及玩家组件先实现必要编解码；未来怪物组件沿用契约。
6. **失败仍卸载。** 临时文件写入失败返回错误事件，Chat 面板追加系统消息；世界组件和区块实体照常卸载。重入读取上次成功记录或配置基准。完整地图仅绘制线框和玩家点，不读取 tile 数组。

## Risks / Trade-offs

- [单文件工作存档在每次卸载时重写] → 只记录改变区块，写入时使用临时文件替换；当前配置规模足够，未来按实际性能再拆分文件。
- [写入失败后改动丢失] → Chat 系统消息清楚说明区块和后果，内存回收仍执行。
- [旧槽位格式不兼容] → 新格式带版本；旧格式可在读取时迁移或明确标为不兼容，保证不部分恢复。
- [活跃窗口超过回环世界尺寸] → 活跃数据以规范 ID 去重，行走实例单独计数，避免提前释放。

## Migration Plan

先完成 `main` 的通用 ECS 父子关系及核心测试并提交；合并 `main` 到 `develop` 后实现世界层加载、工作存档、Chat 与功能测试。保留五个正式槽位路径；使用格式版本辨识旧数据。运行项目检查并归档两个 change。
